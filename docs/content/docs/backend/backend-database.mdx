# 后端数据库

## Studio 结构基线 v98

开发、测试和部署统一使用 PostgreSQL。`database.Open` 默认使用 `postgres`，必须配置 `DATABASE_URL`，其他驱动直接拒绝。Redis 用于限流、并发槽位和跨实例协调，启动必须配置 `REDIS_URL`。数据目录保存技能包、临时媒体和加密设置密钥。

`MigrateStudioSchema` 从空库建立 `StudioModels()` 中的业务表，写入唯一一条版本 98 `studio_platform_identity` 记录。重复执行校验版本和 checksum，PostgreSQL advisory lock 串行化迁移。服务启动和 ready 检查使用同一基线。下文旧版本编号用于字段溯源，v98 直接创建当前结构。

| 范围 | 当前持久化边界 |
| --- | --- |
| 画布、项目、偏好 | operations、快照、项目、素材和既有用户数据键直接按 Platform ID 隔离 |
| 创作和 Agent | 保留 Task、Creation、Pi 会话、事件、记忆、审批、恢复和业务资源引用 |
| Platform 素材和执行 | `studio_material_*`、`studio_executions`、`studio_media_actions` 与别名保存固定引用和加密委托 |
| 技能和创作目录 | 保留 Skills、版本、文件、分类、策展、工具、提示词和创作预设 |
| 运行设置和审计 | `system_settings` 保存 Studio 创作及运行参数，业务维护写入审计记录 |
| 退役领域 | 空库不创建 users、user_identities、本地认证、验证码、短信、分组、钱包、账本、支付、扩容订阅、推广、渠道、公告、反馈或平台插件状态表 |

## Platform 主体与作者

业务归属字段直接保存 Platform 数字用户 ID 的规范十进制字符串。`StudioCurrentUser` 将当前 Identity 响应投影成请求内用户对象，登录不写入本地账号或身份映射。同名账号按各自 ID 隔离。

`PlatformAuthenticated`、`PlatformSessionID` 和动作权限仅存在于请求内。当前 `studio:admin` 产品角色映射到 `content:manage`、`skills:builtin:delete`、`skills:categories:write` 和 `skills:curation:write`，每次请求重新校验。技能作者展示与检索使用 `author_name`、`author_avatar_url` 快照，创建、导入和元数据修改由 handler 注入当前已验证主体。

浏览器缓存采用 `oceanway-studio-platform-id-v1` 命名空间。旧 UUID 草稿保留在旧命名空间，当前应用不载入。写请求同时核对身份版本和标签页主体，账号切换前先停止生成消费者并完成原 scope 的本地写入，再清空缓存和恢复新主体。

## 旧测试库清理

用户已确认无 Studio 业务用户，采用清理后建立新基线的方式。未知表、未收尾 Task 或 Agent 会阻止执行。命令操作显式指定的 PostgreSQL 数据库和 schema，默认输出逐表计数。

```sh
cd backend
# DATABASE_URL 指向待处理的 Studio 测试库
go run ./cmd/migrate-schema reset-studio
# --apply 需要原 STUDIO_*、CANVAS_BACKEND_DATA_DIR 和 .settings-key
go run ./cmd/migrate-schema reset-studio --apply
go run ./cmd/migrate-schema status
```

清理前停止 Studio 实例。执行顺序为读取并校验 Platform binding、释放产品引用、释放原执行授权、删除已登记的 Studio 表、建立 v98。操作只释放本产品绑定和委托，Platform 账号、账务与素材原件由 Platform 管理。

`studio_reset_releases` 记录已确认的释放项。远端响应未知或释放失败时，业务表保留，成功项提交到日志，重入继续处理剩余项。缺少有效素材委托时需原用户刷新授权，缺少原密钥时停止清理。旧 UUID 推导仅用于离线核对原数据所属 Platform Origin。

旧结构和未登记业务数据无法通过普通 `up` 接入新基线。旧制品无法通过 v98 ready 校验，回退需使用与制品匹配的数据库备份。SQLite 运行驱动、本地备份/VACUUM 路径和 SQLite→PostgreSQL 搬迁程序已退出。

任务资金回执保存在已有 `tasks.result_json`，`Task.PlatformBilling` 是 `gorm:"-"` 输出投影。任务读取不查询或创建本地账务表。旧渠道路由与账务代码仍有源码清理余项，进度按 WP-STUDIO-020 登记。

## PostgreSQL 测试

`internal/testdb.Open` 要求 `CANVAS_TEST_POSTGRES_DSN`，每个测试创建独立 schema，结束后清理。`Reopen` 在同一 schema 建立另一个连接池，用于多连接事务验证。Studio 路由夹具启动独立 Redis，避免限流和租约串扰。依赖缺失会使测试失败。

下列创作表在基线中保留。路由是否开放由 `RegisterStudioAPI` 决定，保留表结构不代表对应入口已完成 Platform 接入。

Agent 修复复用现有数据列。Task 的 `AgentStatus`、`AgentCleanupPending` 为 `gorm:"-"` 读取投影，原根任务仍以 `text_replay` 保存。原始 Platform relay ID 写入 `provider_request_id`，原生响应的真实用量写入 `result_json.usage`。冻结模型能力和校验后的图片字节进入已有加密 execution envelope，原始签名访问地址仅供服务端下载。终态清理使用 CloudAgentExecution 的控制列，因此运行快照损坏时仍可清理活动步骤及引用。

Studio schema 95 新增 `studio_material_authorities`：用户 ID、用户/Host/平台 SID 的 SHA256 摘要主键、加密的素材委托授权、到期时间和更新时间。不保存 Cookie 或原始 SID，不返回公共 JSON；授权只允许素材访问，由 Platform 校验原会话撤销。每次刷新授权清理到期记录，缺失或不足一分钟有效期需重新初始化素材会话。`User.PlatformSessionID` 为请求内字段，不写数据库。

Studio schema 94 新增 `studio_executions`：任务 ID、用户/command 唯一键、不可变意图摘要、加密的原生请求/执行授权/响应、派发状态和授权释放状态。Cookie 不持久化；原请求字节与授权不进入公共 Task JSON。与 OAC Task 事务入队，发送前以租约和状态 CAS 保证只有一次模型 POST；未知结果只恢复原请求。运行与恢复必须保留数据目录的 `.settings-key`。

## OceanWay Studio 素材引用（Schema 93）

`studio_material_uploads` 保存按用户隔离的稳定上传命令、文件意图 JSON 和 Platform upload_id；同命令不同意图拒绝。`studio_material_references` 以 Resource ID 为主键，固定 account owner、asset_id、version_id、file_id、SHA256、十进制字节数和 binding_id，`(user_id,asset_id,version_id)` 唯一。采用时与 pending Resource 同事务建立引用，确认平台 binding active 后 Resource 才 ready；未知响应按原命令恢复。

这两张表不存原件、上传票据、签名 URL、Cookie、产品密钥或素材授权。Resource 的 provider 固定 platform，object_key/public_url 留空，只保留画布所需元数据；平台后续的新版本不会替换已有画布引用。容量和文件删除仍由 Platform 控制，本批未开放删除。

## 短剧草稿表单（Schema 90）

版本 90 `drama_draft_form` 给 `drama_productions` 增加 `draft_json`（text，默认空串）。创建页“保存为草稿”（`start=false` 且带 `draft`）时写入 `{ sourceText, styleId }`：导入的原始正文和画风 ID，回到创建页时按当时的分集方式重新拆章。只在 `status=draft` 时有值，开工（创建或草稿替换时 `start=true`、制作台“开始制作”）时清空。旧作品为空串，草稿只能在制作台开工。

重存草稿在同一事务内删掉该作品的原著章节（`project_units.kind=chapter`）和 `drama_episodes`，按新表单重新写入，并更新 `projects` 的名称、画幅和素材类型以及 `drama_productions` 整行；仍是草稿且没有任何 `drama_jobs` 时才执行。

## 灵感上新（Schema 87）

版本 87 `inspiration_feed` 只建一张新表 `inspiration_feed_entries`，不改写既有数据。表中是后端定时从 GitHub 上的 YouMind 提示词库和 awesome-seedance 同步的灵感条目，只收正文已是中文的条目。

| 字段 | 说明 |
| --- | --- |
| `id` | 主键，形如 `youmind:<站内 ID>`、`seedance:<slug>`，与前端静态目录同形，前端按它去重 |
| `source_id` / `mode` / `title` / `description` / `image` / `prompt` / `category` / `tags` / `credit` / `source_url` | 展示字段；`tags` 为 JSON 文本；`image` 只接受 https，`source_url` 只接受 http/https |
| `content_hash` | 内容摘要；同步时内容不变就不改写 |
| `published_at` | 上游发布时间，可为空 |
| `first_seen_at` | 本站首次收录时间，只在新增时写入；前台据此标记「新」和排序 |

开关与同步记录存在 `system_settings`：`inspiration_feed` 为 `{enabled}`（缺省为开启），`inspiration_feed_sync` 为最近一次同步的时间、触发方式、各来源结果和上游分类名。两者分成两个键，后台同步写记录时不会覆盖管理员刚改的开关。上游删掉的条目不删除；关闭上新后公开接口不再返回任何条目。

## 站点姿势库（Schema 85）

版本 85 `pose_library` 只建两张新表，不改写既有数据。代码仓库和镜像不携带姿势图片，图片由管理员同步到数据目录 `pose-library/<条目ID>/`（`image.*` 原图、`thumb.*` 缩略图），不进入 `resources` 表，也不计入任何账号的上传额度和文件容量。导入与同步流程见 [姿势库](/docs/canvas/pose-library)。

| 表 | 用途 | 关键边界 |
| --- | --- | --- |
| `pose_library_sources` | 导入来源及署名（`key` 主键、名称、署名、主页、同步用的 `base_url`） | 同一来源重复导入只更新署名和地址；来源下没有条目时随最后一次删除一起移除 |
| `pose_library_items` | 每行是一个姿势的一个视角：`source_key + external_key` 唯一，`group_key` 把同一姿势的多视角归为一组；`system / category / name / angle / code` 为展示与筛选字段，`search_text` 为小写检索文本 | `status` 为 `pending`（待同步）/ `ready`（文件已落盘）/ `failed`（`error` 记录原因）；用户只看到 `enabled = true` 且 `ready` 的条目。`remote_thumb / remote_image` 是导入时拼好的下载地址，`image_file / thumb_file` 是相对 `pose-library/` 的落盘路径，`image_sha256` 用于用户选用时的上传幂等键 |

重新导入只更新元数据和下载地址，已同步的文件不动，`failed` 条目回到 `pending`。删除条目先删记录再清理图片目录；用户已插入画布的姿势图是选用时复制出的用户资源（`resources` 行，按普通上传计入该用户额度），不受删除影响。

## 技能管理员修改记录（Schema 83）

版本 83 `skill_admin_edits` 为 `skills` 增加两个可空时间列，旧技能均为空，同步行为不变：

| 列 | 含义 |
| --- | --- |
| `admin_info_edited_at` | 管理员最近一次修改基本信息的时间。非空时内置技能启动同步不覆盖名称、简介、分类、`markdown_url`、`showcase_media_json`、`extra_info`；GitHub 同步保留名称和简介 |
| `admin_content_edited_at` | 管理员最近一次在后台保存文件并生成新版本的时间。非空时内置技能启动同步不再用内置文件包生成新版本，也不覆盖 `instruction` |

`skills.status` 为 `1` 表示上架、`0` 表示下架，只由后台上下架接口修改；内置技能启动同步和整行保存都不写该列。

## Agent 记忆文件列补齐（Schema 77）

版本 77 `agent_memory_document_columns` 只做补列：确保 `agent_memory_documents.next_entry_seq` 与 `agent_memory_document_revisions.call_id` 存在，并把空值回填为 `0` / 空串。开发期的早期构建执行 v76 时这两列还没加入模型，v76 已记为完成、校验和不能再改，缺列会让创建 Agent 轮次时读取记忆文件失败（`no column named next_entry_seq`）。新库由 v76 一次建全，v77 是空操作；不改写既有记忆内容。

## Agent 记忆文件与技能自动发现（Schema 76）

版本 76 `agent_memory_document_skill_discovery` 新增两张表，并给 `user_skill_states` 补 3 列，不改写既有数据：

| 表 / 列 | 用途 | 关键边界 |
| --- | --- | --- |
| `agent_memory_documents` | 每个用户一份长期记忆文件：`entries_json`（条目数组，每条含 `id`、`section`（`user` 关于用户 / `notes` 工作笔记）、`text`、`source`、`originRunId` 和时间）、`next_entry_seq`、`revision`、`hash`、`char_count`、`mode`（`auto` / `review` / `off`）、`capacity`（默认 5000 字） | 主键 `user_id`；写入按 `revision` CAS；条目 ID 由单调序号生成，删除后不复用；单条最多 400 字、全文最多 80 条；正文只是参考数据，不授予工具、预算或审批权限 |
| `agent_memory_document_revisions` | 每次修改的前后快照：`actor`（`agent` / `user` / `restore` / `seed`）、`status`（`applied` / `pending` / `rejected`）、`run_id`、`call_id`、`summary`、`ops_json`、`before_json` / `after_json`、`decided_at`、`restored_at` | `(user_id, created_at)` 复合索引；同一工具调用的 `call_id` 重放时返回已有结果，不重复写入；每个用户只保留最近 100 条已结束的修订，待确认修订不裁剪且最多 20 条 |
| `user_skill_states.agent_mode` | `auto`（默认，空串视同）或 `manual` | `manual` 不进 Agent 的自动发现目录，只在用户点名或为对话固定时可用 |
| `user_skill_states.agent_use_count` / `agent_last_used_at` | Agent 成功读取该技能文件的次数与最近时间 | 只用于预算不够时决定目录里谁先列出，不是效果评分 |

第一次读取某用户的记忆文件（打开设置或 Agent 运行）时创建文档，并把该用户已批准的旧版 `agent_lessons` 导入为一次 `seed` 修订，用户可以撤销。旧表、导出接口和管理员巡查暂时保留，Agent 不再读写；旧版压缩调度不再启动。

## 短剧剧情段参考图指定（Schema 74）

版本 74 `drama_segment_references` 为 `drama_segments` 增加 `reference_cast_ids_json`（text）。空串表示按本段镜头自动取参考图（角色、道具、场景依次编号）；非空是用户指定的设定 ID 数组，顺序即“参考图N”编号，`[]` 表示本段不发参考图。旧段为空串，行为不变。`drama_productions.settings_json` 新增 `referenceLimit`（0–20，0 为按视频模型上限），只约束自动取参考图的段，超出的设定按文字描述提交；手动指定的段只受模型图片上限约束。

## 短剧单集素材类型（Schema 73）

版本 73 `drama_episode_source_format` 为 `drama_episodes` 增加 `source_format`（最长 16 字）：`novel` 小说原文需改编，`script` 用户写好的剧本只拆镜、台词逐字保留，`storyboard` 用户做好的分镜按原镜头转录。旧集为空串，按 `novel` 处理。分镜原文是 JSON（`{"shots":[…]}` 或镜头数组）或带表头的 Markdown 表格 / 制表符文本时，剧本阶段直接解析入库，不调用文本模型。

逐集追加（`POST /dramas/:id/episodes`）在同一事务内写入一行 `project_units`（`kind=chapter`，`position` 为末尾）和一行 `drama_episodes`（`number` 为当前最大值 + 1），并把 `drama_productions.plan_cursor` 推过这一章、保持 `plan_done=true`，调度循环不会再把这一章交给分集规划；`plan_done=false` 时拒绝追加。

插到某一集前后（同一接口带 `anchorEpisodeId` / `position`）不改表结构，在同一事务内完成：新集的 `number` 取锚点集号（之前）或锚点集号 + 1（之后），这个号及之后的集整体 + 1；新章节的 `position` 取锚点集章节的最小值（之前）或最大值 + 1（之后），这个位置及之后的章节（含预留章节）整体 + 1，`drama_casts.look_from_chapter` / `look_to_chapter` 中不小于新章节号的值同步 + 1。删除一集（`DELETE /dramas/:id/episodes/:episodeId`）在同一事务内删除本集的 `drama_takes`（段视频与成片版本）、`drama_jobs`、`drama_segments`、`drama_shots` 与 `drama_episodes` 行，之后的集号整体 − 1；只属于这一集的章节改为 `status=reserved`，`plan_cursor` 重算为已加入制作的章节数。`(project_id, number)` 唯一，集号平移先把受影响行写成负数再写回目标值，避免逐行加减时撞号；`title` 仍是“第 N 集”的集与 `drama_jobs.label` 开头的“第 N 集”随新集号改写（标签改写不更新 `updated_at`）。删除后不再被引用的段视频、尾帧与成片资源按孤儿资源规则清理。

导入长篇时只选部分章节：没选中的章节同样写入 `project_units`，`status=reserved`（预留，未加入制作）。资产提取、分集规划与规划游标 `plan_cursor` 只看 `status<>reserved` 的章节；加入制作（`POST /dramas/:id/chapters/produce`）在同一事务内把章节改为 `ready`、追加对应的 `drama_episodes`，并把 `plan_cursor` 设为已加入制作的章节数，只在 `plan_done=true` 时允许。

版本 78 `drama_cast_voice_looks` 为 `drama_casts` 增加角色声音与造型列，为 `drama_shots` 增加镜头造型选择：`voice_profile_id` / `voice_sample_resource_id` 是角色指定的声音（声音库条目与样本音频），支持参考音频的视频模型在该角色开口的剧情段里随请求发送样本；`parent_id` 非空表示这一行是所属角色的一套造型（妆造），`look_name` 造型名、`appearance` 是这套造型的外观、`look_from_chapter` / `look_to_chapter` 是默认适用的原著章节号（从 1 起，0 不限），名称、别名与声音沿用角色本体；造型参考图以角色本体参考图为底图 `image_to_image` 生成，保持同一张脸。`drama_shots.look_cast_ids_json` 是本镜出镜角色选用的造型行 ID 列表，空表示用本集默认造型或角色本体；取参考图时用造型行的外观与参考图替换角色本体。旧数据这些列为零值（角色本身、无指定声音、各镜用本体）。资产提取（作品圣经）为角色输出 `looks`，剧本为每镜输出 `looks`（角色名 → 造型名）并可在 `cast` 里用 `kind=look` 即时建新造型。

## 短剧参考控制与造型提示词（Schema 92）

版本 92 `drama_reference_controls` 增加以下 text 列，不改已有参考图与媒体内容：

| 表 / 列 | 含义 |

| `drama_casts.image_prompt` | 用户为造型保存的生图提示词，最多 12000 字；空时按外观描述生成，并保持角色本体形象一致 |

## 短剧自动制作（Schema 61–67）

剧情段按连续场景切分，并保证每段总时长不超过所选视频模型的单次上限；单个镜头超过上限时改编失败并提示调整分镜规则。第 2 段起的视频请求以上一段视频的最后一帧作为首帧（`image_to_video`），上一段未生成时本段排队等待；开场段使用参考图（`reference_to_video`），模型不支持时退回 `text_to_video`。参考图按“角色 → 道具 → 场景”编号，与提示词里的“参考图N”一致，提交时在提示词开头追加对应说明。最后一帧由后端用 ffmpeg 抽取，镜像需包含 ffmpeg。

作品设置 `settings_json` 保存画幅、单集时长 `episodeSeconds`（30–1200 秒）、风格、对白语言、审阅方式 `reviewMode`（sample 先完整做出第 1 集样片 / every 每集确认提示词 / auto）、生成节奏 `mediaMode`（manual 新作品默认，先只跑文本 / auto）、参考图方案 `assets`、分镜规则 `storyboard`（剧情段切法 `segmentMode`：auto 智能，在场景切换处断开、单段不超过视频模型单次上限；fixed 固定，每段 `segmentSeconds` 秒、只按时长装箱；range 范围，每段 `segmentMinSeconds`–`segmentMaxSeconds` 秒，达到下限后在场景切换处断开。秒数 4–60，三种模式的数值都保存，任何模式实际都不超过视频模型单次上限；`pacing` rapid/fast/standard/relaxed/slow 决定单镜 1.5–3 / 1.5–4 / 2–6 / 2.5–8 / 3–10 秒（缺省 fast）；`dialogue` dense/standard/sparse 约每 3 / 4.5 / 7 秒一句台词或旁白，单句 12 / 16 / 20 字、气口 0.3 / 0.5 / 0.5 秒，语速统一每秒 4.5 字；custom 时按 `speechRate`（语速 2–8 字/秒）、`lineSeconds`（每句间隔 1.5–20 秒）、`lineMaxRunes`（单句 4–40 字）、`linePauseMs`（气口 100–2000 毫秒）计算镜头时长并写进剧本与段视频提示词，缺项按标准档补齐，切回预设档时保留这四项；`transition`、`transitionMs`（150–1500 毫秒，缺省 150））、视频提示词技能 `promptSkill`（`skillId`、`skillName`、`path`，撰写段提示词时把该技能文件全文交给文本模型；保存与撰写时都校验当前用户可读，不可读直接报错）、并发与 text/image/video 三类模型。旧版分镜规则字段 `durationMode`、`fixedSeconds`、`minSeconds`、`maxSeconds` 已删除，读取时忽略，下次保存设置即从 JSON 中去掉。

`settings_json` 另有以下可选键，不改表结构，旧作品缺省时按括号里的默认处理：`videoResolution`（剧情段视频分辨率，取自视频模型声明的档位；空为模型默认）、`bibleSkill` / `scriptSkill`（资产提取、分镜拆分的写作技能，格式同 `promptSkill`；空为内置规则）、`storyboard.performance` 与 `storyboard.cameraMotion`（1–10 整数，缺省或 0 按 5）、`assets.propResolution` / `assets.sceneResolution`（道具、场景参考图分辨率；`assets.resolution` 只用于角色参考图，旧作品的道具、场景改为按模型默认档位）、`models.bibleText` / `scriptText` / `promptText` / `characterImage` / `propImage` / `sceneImage`（按步骤或参考图类型单独指定的模型，空为沿用 `models.text` / `models.image`）。剧情段工作的 `payload_json` 增加 `maxChars`（撰写时的正文字符上限）与 `condensed`（本次已自动精简次数），只在调度内部使用。

Schema 67 `drama_segment_production` 从逐镜流程迁到剧情段流程：先把镜头上已有的配音/首帧/视频资源归档为历史版本，再删除 `drama_shots` 的 `video_model_json`、`speaker_cast_id`、`frame_prompt_override`、`video_prompt_override`、`audio_*`、`frame_*`、`video_resource_id`、`video_status`、`approved`、`locked`、`error`，删除 `drama_casts.voice_key` 与 `drama_episodes.frames_approved`，新增 `drama_episodes.approved`、`drama_shots.prop_ids_json` 与 `drama_segments` 的视频列。存在旧逐镜数据时，未完成的集回到剧本阶段、作品暂停并提示重新改编，排队中的旧工作取消，不会自动重发收费任务。Schema 62–66 是同一功能的中间版本（剧情段字段、工作历次提交、手动放行、转场、剧情段表）。

旧的章节分镜工作流表（`shots`、`shot_revisions`、`shot_artifacts`、`workflow_*` 等）不再有页面入口，本次迁移不删除这些表和数据。

## Agent 记忆审批与恢复（Schema 58）

迁移 `agent_memory_proposals`（Schema 58）保留既有记忆内容，给 `agent_lessons` 增加 `origin_run_id`（来源运行、带索引）和 `evidence_json`（事件序号、调用 ID、工具名数组）；给 `agent_memory_settings` 增加 `compact_proposal_id` 和 `compact_cursor`，并创建下列两张表。Studio v98 新库直接注册这些模型。

| 表 | 保存内容 | 并发与归属边界 |
| --- | --- | --- |
| `agent_memory_proposals` | `user_id`、`task_id`、`status`、`version`，精确输入 `input_json`、拟改动 `changes_json`、摘要 `summary_json` 及创建/更新时间、决定时间 | 按用户查询；生成回调绑定提案、任务和版本，只从 `generating` 变为 `pending` / `no_changes` / `failed`，不修改已批准记忆 |
| `agent_memory_revisions` | `user_id`、唯一 `proposal_id`、`version`、应用前 `before_json`、应用后 `after_json`、创建时间及 `restored_at` | 仅批准成功时创建；恢复按所有者、版本与应用后快照校验，只允许一次成功恢复 |

批准或拒绝必须提交列表中读到的提案 `version`。批准在同一事务内 CAS 提案、锁定全部源记忆并校验内容版本，再执行改写/合并及保存恢复快照；任一源记录发生编辑、状态变化或缺失，整批回滚。内容版本覆盖正文、步骤、来源、状态、更新时间、验证时间和运行/工具证据，排除仅表示读取活动的 `hits` / `injected` 计数。

压缩不刷新 `last_verified_at`，不覆盖来源运行或执行证据；合并保留第一条的原始来源，所有源记录的完整来源同时保存在恢复快照。恢复要求当前条目仍匹配应用后快照，且原先删除的 ID 没有被任何新记录复用；它不覆盖后续编辑或他人记录，也不抹掉审批历史。快照与提案和记忆一样属于用户私有数据，不保存 API Key、Cookie 或素材正文。

每批最多 80 条，模型输入最多 48 KiB；按稳定 ID 从 `compact_cursor` 继续并循环到库尾，游标只推进到实际进入输入的最后一条，不再固定读取 Hits 最高的 80 条。任务启动前原子保存输入快照和提案；旧设置版本不能重复认领任务，迟到的状态或回调不能覆盖新提案。`last_status` 区分 `queued`、`running`、`awaiting_review`、`applied`、`rejected`、`restored`、`succeeded`（无可应用修改）和 `failed`。

升级先运行 `migrate-schema up` 与 `verify`。迁移 58 不修改版本 1–57 的名称和校验和；新增表及证据字段不等于已验证记忆质量，真实模型召回和创作效果仍需独立评测。

## 素材资源引用边界

资源引用快照同时读取素材表现的 `resource_id` 和 `metadata_json`（包括嵌套资源字段）；不能先按 `resource_id` 过滤表现记录，否则仅在 metadata 中引用的共享资源会漏检。素材批量删除保留其他素材仍引用的资源；管理员删除也复用这一引用边界。

短剧表直接持有的资源不在任何 JSON 文档里，单独查询并记为 `短剧` 引用：`drama_casts.image_resource_id`、`drama_segments.video_resource_id` / `tail_frame_resource_id`、`drama_episodes.final_resource_id` 与 `drama_takes.resource_id`（只看当前用户的作品）。素材“彻底删除”和 24 小时孤儿资源清理都保留这些资源；此前它们未纳入引用快照，上传的参考图与段视频尾帧可能被误清理。

Studio 引用快照跳过已退出的公告和反馈表。Platform Resource 在本地物理清理事务中受保护，正式路由当前禁用永久删除。

## 画布 operations 与幂等回执

| 表 | 用途 | 关键边界 |
| --- | --- | --- |
| `canvas_projects` | 当前画布内容及递增 `revision` | 所有正常画布写入都通过 operations 服务更新；对象删除后迟到更新不能隐式重建 |
| `canvas_mutation_receipts` | 保存 `(user_id, canvas_id, mutation_id)`、请求摘要、提交摘要 `result_json` 和提交 revision | 唯一请求身份与画布内容在同一事务提交；同 ID 不同摘要返回冲突；`result_json` 不含画布正文；创建超过 7 天的回执由后台 worker 每小时分批删除 |

`canvas_mutation_receipts` 不保存整批历史版本，也不保存画布正文，只保存一次请求的恢复摘要。早期构建在 `result_json` 中写入整份画布，每次编辑一份且从不清理，表随编辑次数线性增长；升级后旧回执在 7 天内被清理。PostgreSQL 删除行后空间只供表内复用，不归还磁盘；需要回收磁盘时先备份，在维护窗口执行 `VACUUM (FULL, ANALYZE) canvas_mutation_receipts;`（会锁表），或用 `pg_repack` 在线重整。服务端在事务内锁定画布、创建或读取 receipt、校验字段/对象基线、应用 operations、递增 revision、写入结果并完成 receipt；事务失败时不留下可重放的半成品。客户端可在响应丢失、断网或刷新后用原始 `mutationId` 和原始 payload 重放。

画布操作支持 `create_canvas`、`create_node`、`patch_node`、`remove_node`、`create_connection`、`update_connection`、`remove_connection`、`set_field`。创建操作显式创建对象；更新和删除要求对象存在，并以 `before`、`expected` 或 `beforeValue` 做字段/对象级并发校验。删除节点同时删除其连接，迟到的媒体回写返回对象缺失冲突。`viewport` 是本地视图状态，不进入远端 operations。

旧的画布版本历史、恢复和整批 PUT 不属于当前用户写入合同；数据库迁移保留既有历史表以兼容已部署数据，但新写入不依赖它们。Agent、媒体回写、预演台、创作提交及导入路径都复用同一 operations 服务。

画布/素材结构化配额使用 `UserStructuredStorageUsage`，仅聚合当前用户的 `assets` 和 `canvas_projects` 数量及 `payload_json` 字节数。PostgreSQL 使用 `octet_length(...)`，避免中文按字符计数；空值按零字节处理。operations 通过事务 repository 读取用量后再写入，不增加缓存或配额表，不变更 schema。完整 `UserStorageUsage` 仍用于需要任务及日志统计的路径，画布保存不再为未使用的任务/日志指标扫描大字段。

## 已部署 PostgreSQL 的素材 bytes 修复

升级到包含修复工具的镜像后，由部署管理员执行一次，无需终端用户修改数据库、清缓存或重建画布。旧镜像不支持以下子命令；请先将部署配置中的镜像版本更新为实际发布的修复版本。此操作不增加表或改变 schema 版本，也不会在启动时静默修改素材。

`migrate-schema repair-asset-bytes` 默认只检查，`--apply` 才写入。它按 100 条分批扫描媒体素材，只修复无效的 `data.bytes`，从明确的 `resource:` 引用取得同用户、同类型、就绪且大小为正的资源 `size`。JSON 其他字段、素材 ID、文件和项目引用保留，仅同步推进素材及 JSON 的 `updatedAt`。没有可靠资源或存在其他合同错误的素材保持原样并列入 `unresolved`；存在未解决记录时命令非零退出，即使其他可修复记录已成功提交，也不代表全部修复。

在原部署目录使用原来的环境文件执行；若部署使用了额外 Compose 文件，所有命令必须沿用相同参数。下面对应仓库标准 PostgreSQL Compose：

```bash
# 先下载实际发布的修复版本，再只读检查；不会启动后端。
docker compose -f docker-compose.deploy.yml pull migrate backend web
docker compose -f docker-compose.deploy.yml run --rm --no-deps migrate repair-asset-bytes
```

审阅报告，确认可修复范围后再进入维护窗口。多副本/独立 worker 也必须全部停止写入。备份或校验失败时停止操作，不能继续执行修复：

```bash
docker compose -f docker-compose.deploy.yml stop backend

# 备份必须成功才可继续。备份含用户数据，限制权限，不上传或提交仓库。
umask 077
backup="asset-bytes-before-$(date +%Y%m%d-%H%M%S).dump"
docker compose -f docker-compose.deploy.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup" || exit 1
docker compose -f docker-compose.deploy.yml exec -T postgres pg_restore --list < "$backup" > /dev/null || exit 1
```

确认备份和检查均成功后执行写入，保留 JSON 报告：

```bash
docker compose -f docker-compose.deploy.yml run --rm --no-deps migrate repair-asset-bytes --apply
docker compose -f docker-compose.deploy.yml run --rm --no-deps migrate repair-asset-bytes

# 核查 repaired / unresolved，再恢复服务。
docker compose -f docker-compose.deploy.yml up -d backend web
```

若报告仍有 `unresolved`，需按素材 ID 核查实际文件大小及引用；不要批量填零，也不要把未解决记录删除。工具不访问外部 URL，不下载媒体。应用后让用户重新加载素材库验证；不会要求清空本地存储。若数据库更新失败或检测到并发修改，整批写入事务回滚，`repaired` 为零。已成功提交后的回滚应在隔离数据库恢复备份并核查，再选择性恢复相关记录；不要在恢复写入后直接覆盖整库，以免丢失后续数据。

## 平台外观配置

当前外观 JSON 合同版本为 8，主题参数新增 `skinThemes[].tokens.buttons.light/dark`：填充模式、角度、常态/悬停/按下双色和文字色。经典与内置主题默认均为纯色墨色主按钮，旧主题缺少此块时补入纯色；公开 `activeSkin` 使用相同结构。无表结构迁移，读取补齐只在内存执行，管理员保存时写回。回退应用版本前保留外观 JSON 备份，旧版本不支持新按钮填充参数。

平台外观复用既有 `system_settings` 表，不新增结构迁移。键 `appearance` 的 JSON 值使用版本化合同；版本 3 保存品牌名称、英文品牌标识、登录页主标题与可选说明文案、浅色与可选深色 Logo 资源 ID、Logo 外框开关、登录页视频资源 ID、可选封面资源 ID 和预留皮肤 ID。只配置一套 Logo 时，公开投影会在浅色和深色主题复用同一资源；旧版本缺少深色 Logo 与外框字段时分别回退到单 Logo 和启用外框，不改变既有视觉。资源元数据和文件仍分别由 `resources` 表与当前资源存储承担。恢复默认外观时删除这条设置记录并回到内置值，不级联删除已经上传的资源。

公开接口只投影品牌名、英文品牌标识、登录页公开文案、深浅主题使用的稳定 slot 资源 URL、Logo 外框状态、配置状态和修订标识，不返回内部资源 ID、对象路径或存储凭据。管理员保存新配置前，服务层会校验文本长度与安全字符、资源为就绪状态、类型与 slot 匹配，且新绑定资源由当前管理员上传；两套 Logo、视频和封面中任何正在使用的资源都会进入管理员删除保护。品牌变更同时写入 `admin_audit_events`。

规范化技能包保存在后端数据目录的 `skill-packages/<skill-id>/<version-id>.zip`，数据库只保存索引和版本指针。上传 ZIP 时强制校验 `SKILL.md`、路径越界、软链接、重复路径、文件数量和解压大小；GitHub 技能保存公开仓库、分支、子目录和提交 SHA，后台每 6 小时检查一次开启自动更新的技能，并记录最近检查、同步时间及失败状态。

### 长篇项目读取边界

短剧工作台不再通过单个项目详情响应下载全部章节正文、镜头历史、产物、画布和资产。读取按页面职责拆分：

| 接口 | 返回范围 |
| --- | --- |
| `GET /api/projects/:id/core` | 项目基础设置，不包含业务集合 |
| `GET /api/projects/:id/overview` | 项目聚合计数与前 8 个章节进度 |
| `GET /api/projects/:id/units` | 全部章节摘要与字数，不包含正文 |
| `GET /api/projects/:id/units/:unitId` | 单章正文 |
| `GET /api/projects/:id/units/:unitId/workspace` | 当前章节的镜头、版本、产物、引用、候选、相关任务和已绑定资产 |
| `GET /api/projects/:id/canvases` | 项目画布与当前页章节关联，使用 `page`、`pageSize` |
| `GET /api/projects/:id/assets` | 项目资产分页、分类/目录计数，支持分类、媒体类型、目录和关键词筛选 |
| `GET /api/projects/:id/asset-candidates` | 资产候选分页，支持章节、状态、分类和名称关键词筛选 |

场景/道具提取设定复用 `assets.kind=entity` 与 `asset_versions.definition_json`。绑定真实图片后，同一资产转为 `image`，新版本通过 `asset_representations` 的 `primary` 角色关联资源，旧表现记录不删除。画布引用可匹配该资产的服务端历史图片；不通过客户端 metadata 授权历史资源。此流程不增加表或字段。

旧 `GET /api/projects/:id` 暂时保留给尚未迁移的调用方；短剧工作台页面不得重新依赖该整包接口。

面向上千章、上万镜头的数据量，迁移会建立以下组合索引：

- `idx_project_units_project_position`：章节按项目和位置读取。
- `idx_shots_project_unit_position`：当前章节镜头按位置读取。
- `idx_shot_artifacts_project_unit`：当前章节产物读取。
- `idx_canvas_unit_links_project_unit`：章节关联画布聚合。
- `idx_canvas_projects_user_project_updated`：项目画布倒序分页。
- `idx_project_asset_links_project_folder_position`：项目目录资产分页与排序。
- `idx_project_asset_candidates_project_unit_status`、`idx_project_asset_candidates_project_status_category`：章节候选和待确认分类队列。
- `idx_tasks_user_project_created`：项目任务恢复读取。

## 画布生成工具

Schema 30 新增 `tools`，31 新增 `tool_favorites`；主分支已有 28（Agent 执行日志）、29（资源租约）编号和 checksum 不变。

Schema 32 为 `channel_models` 新增 `tags`（TEXT、NOT NULL、默认 `'[]'`），通过 JSON serializer 存储有序的 `{ text, color }` 数组。每个模型最多 5 个标签，文字去除首尾空白后为 1–12 字且不重复，颜色为 `purple/blue/green/gold/orange/pink`。标签仅用于展示，不影响价格、能力和路由。后端启动时执行增量迁移，已有模型默认无标签；回退应用可保留此新增列，若人工删除列会丢失标签配置，须先备份。

- `tools`：自增 `id`、类型 `type`、名称 `label/label_en`、描述/标签、`prompt`、预览 `cover/media_url/extra_info_json`、比例、`owner_id`、`source`、`enabled`、`visibility`、排序权重和时间。
